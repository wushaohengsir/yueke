## 1. 项目背景与问题定义

线下培训机构、独立教师与学员的约课长期依赖微信群等口头方式：老师临时改课、学员约课撞时段、课时账目说不清、请假补课没有凭据，纠纷频发且无从查证。项目组面向这一场景，设计并实现一个轻量级在线约课平台，聚焦一条核心闭环：**老师开放可授时段 → 学员自助约课/请假 → 系统自动防冲突并沉淀全部记录**，作为业务与账目的唯一事实来源。首版不做在线支付及资金往来类模块（涉及资金结算需相应资质），课时交易以线下结算 + 课时包合同入账方式闭环。

## 2. 需求分析与角色划分

系统划分为四种角色，各自职责与核心用例如下：

| 角色 | 核心用例 | 登录态 |
|---|---|---|
| 游客 | 浏览老师与可授时段 | 免登录 |
| 学员 | 自助约课、请假、查课时/历史、签署课时包合同 | 需登录 |
| 老师 | 维护可授时段模板、查看周课表、审批请假、课后登记完成 | 需登录且通过审核 |
| 管理员 | 老师审核、用户/科目管理、数据看板、为学员代约远期排课 | 需登录 |

需求基线在飞书需求文档中随迭代同步修订（原文修订），开发过程以 todos.md 需求清单逐项勾选，保证「清单—版本—提交」三者可对账。

## 3. 总体设计

**技术栈**：前端 Vue 3 + Vite + TypeScript + Pinia；后端 Java 17 + Spring Boot 3 + MyBatis-Plus + Spring Security（JWT）；数据库 MySQL 8.0（utf8mb4 / InnoDB）；部署 Docker Compose（nginx + springboot + mysql）。

**系统架构**：

```
浏览器（Vue 3 SPA，移动端 Web）
   │  REST（/api/*，Authorization: Bearer JWT）
   ▼
nginx（前端静态资源 + /api 反向代理）
   ▼
Spring Boot 3（Controller → Service → Mapper）
   ├─ Spring Security / JwtUtil：鉴权 + 角色越权拦截
   └─ MyBatis-Plus → MySQL 8（yueke）
```

**分层约定**：后端 Controller / Service / Mapper 三层，DTO 与实体分离，统一返回体 `Result` + 全局异常处理；前端按 `views / components / stores / api / utils` 组织，组合式 API + TS 严格模式。

## 4. 数据库设计

按 1NF→BCNF 设计，共 15 张规范化表，覆盖用户角色、科目、分课程课时、时段、预约、请假、流水、合同、商品订单与通知。要点：

- **用户与角色**：`user` 单表 + `role` 枚举（0游客/1学员/2老师/3管理员），与 `teacher_profile`、`student_profile` 1:1 扩展；M:N 一律 Junction 表（如 `teacher_subject`）。
- **金额与课时**：金额用「分」（INT）、课时用整数，全程不用浮点；余额不做派生存列，靠 `credit_log` 流水推导，可审计、可对账。
- **生命周期**：业务对象均用 `status` + 时间戳表达状态机，不做物理删除。
- **分课程课时**：`student_credit(student_id, subject_id)` 唯一约束，课时按课程独立记账、不通用；`contract` 课时包签署生效后自动按课程入账。

**核心创新——预约并发防冲突（book 表）**：MySQL 不支持部分唯一索引，本项目用「生成列 + 组合唯一索引」等价实现：新增生成列 `active_flag = IF(status IN (0,1), 1, NULL)`，即仅当预约处于活跃状态（待确认/已确认）时为 1，请假/取消/完成后自动为 NULL；再建唯一索引 `uk_teacher_active_slot(teacher_id, start_at, active_flag)`。这样「同一老师同一时刻至多一个活跃预约」的约束被强制在数据库层：并发请求同时插入时，只有一条成功，其余因唯一索引冲突被拒绝，应用层捕获后返回友好提示。请假或下课释放时段无需删除记录，状态迁移即释放，历史可追溯。

## 5. 详细设计

### 5.1 约课闭环流程

1. **老师开放时段**：按「星期 → 当天时段」两级模板维护（`timeslot_template`），支持临时屏蔽/加开（`timeslot_block`）。
2. **学员约课**：仅展示后端生成的近期开放可约时段，选课提交 → 事务内插入预约并扣减该课程课时 → 写一条「约课消耗」流水；插入依赖唯一索引天然防并发冲突。
3. **请假审批**：学员提交 `leave_request` → 老师批准则预约置为「已请假」并自动返还课时（记「请假返还」流水），驳回则维持原状；已下课课程禁止请假。
4. **课后登记**：老师确认到课、登记完成，预约转「已完成」。
5. **合同入账**：学员购买课时包生成合同，签署生效后按课程写入 `student_credit`，并记「购买充值」流水。

### 5.2 可约时段体系与互斥

老师可授时段是约课的上游，设计上重点保证「一个老师一个时段只对应一个可约入口」：启用某模板时自动停用同一天与之重叠的其他启用模板（模板互斥）；系统仅把学生自助约课窗口收敛在近期开放时段（当前口径今明两天），从根上消除远期跨周归属歧义，更远期课程由管理员排课代约；服务端在下单前还会按 `isOpenTemplateSlot` 二次校验时段归属，防止绕过前端直接调接口。

### 5.3 权限与安全

- JWT 无状态鉴权；`SecurityConfig` 统一校验，接口层做角色分流与越权拦截（管理员接口强制 `role=3`）。
- 注册闭环：学员/老师分身份注册，老师账号需管理员审核通过方可登录老师端；管理员后台可新建学员/管理员账号、审核可改回。
- 登录态存 `sessionStorage`，多标签页各自登录身份互不串扰，单标签刷新仍保持登录。
- 密码 BCrypt 存储，密钥与本地配置不入库。

### 5.4 前端设计

移动端 SPA，按角色路由分流。学员端：首页（宫格入口）、约课列表/详情、请假、历史、我的、合同；老师端：时段模板、周课表与日详情、请假审批、课后登记；管理端：用户/科目管理、老师审核、数据看板、排课代约。风格上完成红枫主题换肤（米白＋枫红＋青绿描金视觉体系、飘落枫叶动效、统一悬停交互），约课入口与其余按钮一致，不做特殊化。前端架构收敛出 `utils/datetime`（日期格式化唯一来源，消除各视图重复实现）、`utils/status`（状态文案/样式表驱动）、`composables/useLogout`、统一 `api` 层错误模型 `attempt()`。

### 5.5 后端设计

服务按职责拆分为 Auth/Teacher/Booking/Admin/Contract/Block/Subject 等，架构上做了「深模块」收敛：`AuthHelper` 作为 Bearer/JWT 唯一接缝（消除各 Controller 重复解析）；`CreditService` 收敛课时账本（消除四处重复扣减）；`AppTime` 统一时区口径；`OpStatus` 枚举替代 Service 层魔法字符串返回值，配合统一返回体在编译期兜住漏写分支。

## 6. 系统实现与运行结果分析

实现按版本线推进：V0.1 数据库与前后端骨架 → V0.5 四角色联调与防冲突 → V1.0 合同/看板/管理端完善 → V1.3/V1.4 课表两级重构与「仅近期可约/模板互斥」口径 → V1.6 管理员排课 → V1.7–V1.9 主题换肤与前后端架构重构 → 注册闭环与 Docker 部署上线。全程及时提交并双源推送（GitHub + Gitee），提交记录与版本、todos 可互相对账。

运行中出现的主要问题与处理过程：

| 问题 | 原因分析 | 解决与改进 |
|---|---|---|
| 双标签页同时登录会串身份 | 登录态存 localStorage，全浏览器共享、后登录者覆盖前者 | 改 `sessionStorage`，标签页隔离；单标签 F5 仍保持登录 |
| 时段模板可保存倒序时间（如 20:00–19:00） | 前端校验缺失、后端未兜底 | 前后端同时加「结束须晚于开始」校验，非法返回 400 |
| 同老师同时段被约两次 | 仅靠“先查再插”存在并发窗口 | 把约束下沉到数据库：生成列 `active_flag` + 唯一索引（见 §4），并写集成测试验证并发场景 |
| 后端返回 "ok"/"bad_time" 等字符串，写错不报错 | Service 层魔法字符串、由 Controller 背字符串表 | 引入 `OpStatus` 枚举 + switch 映射，编译期查漏；测试断言同步改为枚举 |
| push 被队友新提交挡住 | 本地落后远端 | fetch 确认无冲突后 `pull --rebase` 再推送，避免强推覆盖队友工作 |

## 7. 测试与验收

- 集成测试直连独立测试库，覆盖防冲突、倒序拒绝、停用模板可编辑、审批返还等关键链路，10 个用例全部通过（本机无 MySQL，由组员开发机执行复核）。
- 冒烟验证（公网）：`GET /api/auth/subjects` 返回 `code=0`；对未注册手机号 `POST /api/auth/login` 返回 `code=400`「尚未注册」，确认新代码已上线且未在线插入脏数据。

## 8. 主要创新点

1. **无部分索引的并发防冲突方案**：用生成列 + 组合唯一索引把「活跃预约唯一」约束提升到数据库层，替代 MySQL 缺失的部分唯一索引能力，从机制上根除约课并发双占。
2. **分课程课时账本 + 全量流水**：课时按课程独立、不通用；余额由 `credit_log` 流水推导而非直接存列，约课/请假/购买全部留痕可审计。
3. **“模板互斥 + 近期可约 + 服务端二次校验”的可约时段模型**：以星期模板为唯一可约入口，互斥停用重叠项、收敛自助约课窗口，堵住跨周归属歧义与越权直连接口两个漏洞。
4. **深模块化工程收敛**：前后端分别以 `AuthHelper`/`CreditService`/`OpStatus` 与 `utils/datetime`/`utils/status` 收敛重复逻辑，魔法字符串枚举化，降低长期维护成本。

## 10. 总结与展望

项目在两周内完成了从需求、设计、编码、测试到部署上线的完整闭环，实现了「自动防冲突、记录可追溯」这一核心价值，并获得真实公网环境的验收。不足与展望：①首版未做在线支付（资金结算需相应资质）与消息推送，通知仅站内占位，可接入真实支付与 IM 提醒；②产品已初步支持，可补充商品订单扩展售卖闭环；③并发与权限已有设计，可进一步补充压测与安全审计。整体上，本次实践验证了「数据库层约束优先、账目流水化、状态即历史」三类设计原则，为后续迭代打下了可靠基础。
